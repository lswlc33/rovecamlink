## 1. TUWIN（`com.tuwinsmart.tuwin`）

TUWIN 是唯一把「机型 → 协议」写成代码的品牌：`DeviceType` 枚举 4 个常量，每个绑一份 `DeviceProtocolProfile`（型号白名单 + 探测端点 + 端口/路径白名单）。
证据：`core/domain/model/DeviceType.java:14-18`、`core/network/DefaultDeviceProtocolProfileRegistry.java:19`。

### 1.1 型号清单

| DeviceType | code | 显示名 | 产品类别 | 协议型号串 `expectedModels` | 判定芯片 |
|---|---|---|---|---|---|
| `RIDE3PRO` | `"RIDE3PRO"` | Ride3 Pro | Riding Recorder（骑行记录仪） | `{"R3Pro"}` | 未标注 |
| `RIDE6` | `"RIDE6"` | Ride6 | Riding Recorder | `{"R6"}` | 未标注 |
| `RIDE5` | `"RIDE5"` | Ride5 | Riding Recorder | `{}` → **不做型号校验**，走 `Ride5IdentityPolicy` | Hi3516CV610（身份串 `HI3516CV610-S-FV-CARRECORDER`） |
| `M3` | `"M3"` | M3 | Action Camera（运动相机） | `{"M3", "v57_sport_cam_ezgui"}` | v57 平台（`ezgui` 固件线） |

- 显示名/类别来自资源：`ride3pro`/`ride5`/`ride6`/`device_m3`、`riding_recorder`/`thumb_camera`。
- 适配器只按 `DeviceType` 注册（`DeviceAdapterRegistry.java:24-39`），**没有子型号表**；同一 `DeviceType` 下的硬件差异由固件上报的 `hwver`/`boardversion` 承载（仅 RIDE6 把 `hwver` 记为 boardVersion，`Ride3ProSessionConnector.java:1907-1911`）。
- 未发现自行车灯 / 头盔 / 其它产品线（对 `Bike|Tail|Cyc|Dashcam|尾灯` 全量 grep 为空）。

### 1.2 识别方式

**(a) WiFi SSID —— 两套规则，用途不同，必须都实现。**

扫描推断用锚定正则（`core/util/ConnectUtil.java:33-38`）：

| 常量 | 字面正则 |
|---|---|
| `M3_SSID_REGEX` | `^TUWIN[-_]M3_[A-Za-z0-9]+$` |
| `RIDE3PRO_SSID_REGEX` | `^TUWIN_R3P_[A-Za-z0-9]+$` |
| `RIDE6_SSID_REGEX` | `^TUWIN_R6_[A-Za-z0-9]+$` |
| `RIDE5_SSID_REGEX` | `^TUWIN_R5_[A-Za-z0-9]+$` |
| `RIDE5_PRO_SSID_REGEX` | `^TUWIN_R5P_[A-Za-z0-9]+$` |
| `RIDE5_COMMON_SSID_REGEX` | `^TUWIN_[A-Za-z0-9]{6,}$` |

匹配顺序即优先级：**M3 → RIDE3PRO → RIDE6 → RIDE5**（`ConnectUtil.java:128-147`）。RIDE5 放最后是因为 `RIDE5_COMMON_SSID_REGEX` 是兜底式，会把 `TUWIN_R3P_xxx` 也吞掉。返回 `null` 表示不是本品牌设备。

系统连接用 `PatternMatcher`（**非锚定**前缀，`DeviceWifiNetworkRequestFactory.java:68-85`，flags = `CASE_INSENSITIVE|UNICODE_CASE`）：

| DeviceType | PatternMatcher 串 |
|---|---|
| M3 | `TUWIN[-_]M3_[A-Za-z0-9]+` |
| RIDE3PRO | `TUWIN_R3P_[A-Za-z0-9]+` |
| RIDE6 | `TUWIN_R6_[A-Za-z0-9]+` |
| RIDE5 | `TUWIN_[A-Za-z0-9]{6,}` |

SSID 预处理：`trim()` + 去成对双引号（`normalizeSsid`，`ConnectUtil.java:212-225`）。泛化判定：`isConnectedTUWIN()` = `ssid.startsWith("TUWIN") || 缓存列表包含`（`:125`）。

**(b) 型号字段 —— 探测响应里读哪个 key。**

| 机型 | 响应对象 | 读取的 key | 证据 |
|---|---|---|---|
| RIDE3PRO / RIDE6 | `Ride3ProDeviceInfo` | **`model`**（另有 `uuid`/`swver`/`hwver`/`mac`/`ssid`/`pwd`/`soc`/`features`） | `ride3pro/Ride3ProDeviceInfo.java:18-42`；`Ride3ProSessionConnector.java:1904-1915` |
| M3 | `M3ProductInfoResponse{result,info}` | **`model`**（另有 `company`/`soc`/`sp`），且要求 `result == 0` | `dto/m3/M3ProductInfoResponse.java:74-76,87` |
| RIDE5 | CGI 文本解析出的 `Map` | **`model`，回退 `product`**；`devid`=序列号、`softversion`=固件、`boardversion`=板号 | `Ride5SessionConnector$connectUserInitiated$verified$1.java:136-153` |

`acceptsModel()` 语义（`DeviceProtocolProfile.java:183-206`）：trim 后空串 → false；`expectedModels` 非空 → **大小写不敏感全等**；`expectedModels` 为空 → **一律 true**（所以 RIDE5 不在此把关）。

RIDE5 另有 `Ride5IdentityPolicy.accepts(model, product)`：字面量 `"DBG"`、含 `"R5"`/`"RIDE5"` 的取反分支、以及 `product=="GNR" && model=="HI3516CV610-S-FV-CARRECORDER"` 特例。⚠️ 该方法 jadx 控制流反编译异常，**分支方向属 INFERRED，字面量 CONFIRMED**；接入前需真机抓一次 `getdeviceattr.cgi` 定死。

**(c) 其它标识**：无蓝牙（清单无 BT 权限，包内零 `Bluetooth|GATT`）。MAC 只用于 RIDE5 的 `deviceIdFromBssid`（去分隔符大写、必须匹配 `[0-9A-F]{12}`、黑名单 `020000000000/000000000000/FFFFFFFFFFFF`，`Ride5IdentityPolicy.java:22-37`）。连接后一致性以 **BSSID 优先**（`ConnectUtil.java:170-176`）。

**(d) 探测端点（profile 声明 = 实际调用顺序）**

| 机型 | 声明的 bootstrap | 运行时实际 |
|---|---|---|
| M3 | HTTP:80 `/app/getproductinfo` | 一次调用即定身份 |
| RIDE3PRO / RIDE6 | HTTP:80 `/api/device/status` | **两次**：先 `device/status`，再 `device/info`（身份取自后者，端点证据记前者） |
| RIDE5 | HTTP:80 `/cgi-bin/hisnet/getdeviceattr.cgi` | 一次 CGI，随后过 `Ride5IdentityPolicy` |

身份不符 → `DeviceIdentityMismatchException("Unexpected device identity: expected=…, actual=…, model=…")`（`DeviceIdentityVerifier.java:149-153`）。

### 1.3 连接方式

| 机型 | 默认网关 IP | 控制端口 | 媒体端口 |
|---|---|---|---|
| RIDE3PRO / RIDE6 | `192.168.25.1` | 80 | **8080**（`Ride3ProDeviceAdapterSession.RTSP_PREVIEW_PORT`） |
| M3 | `192.168.169.1` | 80 | RTSP 默认 554，实际从设备返回的 RTSP URI 取；**推送 socket 端口 = `/app/getmediainfo` 响应的 `port`**（校验 `1 ≤ port < 65536`，非法即整个 open 失败，`M3DynamicEndpointPolicy.java:59-62`、`:78`）。`getproductinfo` 的 `sp` 键客户端解析了但**零消费者**，与端口无关 |
| RIDE5 | `192.168.0.1` | 80（CGI） | profile 里 `allowedMediaPorts` 为空（字段层面的事实），但端口**有常量**：直播 RTSP `RTSP_LIVE_PORT = 554`、反向回调 TCP `CALLBACK_PORT = 9002`（`Ride5DeviceAdapterSession.java:53,57`；两处都挂了 `@Deprecated`，仍在 `:250`/`:251` 用来签发 `EndpointGrant`） |

证据：`core/device/DeviceHostPolicy.java:35-48`、`M3DynamicEndpointPolicy.java:21,59-66`、`DefaultDeviceProtocolProfileRegistry.java:19`。

- **只有 WiFi 直连一条路**：`WifiNetworkSpecifier` + `requestNetwork`，**必须带 WPA2 密码**（空密码直接抛 `IllegalArgumentException("Device Wi-Fi passphrase is required")`）；密码是常量 `DEFAULT_WIFI_PASSWORD = "12345678"`（`ConnectedDevice.java:22`），用户从不输入 SSID。
- 两种连接模式（`DeviceWifiConnectRequest.isExact()`）：给了确切 SSID 或 BSSID → `setSsid()+setBssid()`；否则 → `setSsidPattern()`。
- **未发现**：手动输 IP、扫码配网、蓝牙配网。
- 进程级 `bindProcessToNetwork` **不是主路径**，只在「平台不肯给 SSID」时作为探测兜底（`TemporaryProbeBindingLease.java:42-54`，要求 `permit.ssidReadable == false` 且有 routeRevision）；常态是把 OkHttp/Retrofit 绑到 `Network` 对象上。
- **连接工程数值（我们超时/重试默认值的参照，CONFIRMED）**：`WifiNetworkSpecifier` 要求 **SDK ≥ 29**（低于抛 `DeviceWifiRequestFailure.UNSUPPORTED_ANDROID_VERSION`，`DeviceNetworkController.java:272`）；路由 lease 替换等待 **3000 ms**、替换轮询 **50 ms**（`DeviceNetworkController.java:62`、`:61`）；主动 Wi-Fi 扫描等待 **8000 ms**（`DeviceWifiScanner.java:42` `DEFAULT_SCAN_TIMEOUT_MS`）。
- 断线恢复：`RecoverableDeviceControlChannel.recoverControlChannel()` + 路由版本变更时 `invalidateForRoute()` 级联重建（`DeviceSessionManager.java:353-368`、`:251-280`）。

### 1.4 通讯方式

| 机型 | 传输 | 路径前缀 | 命令形态 |
|---|---|---|---|
| RIDE3PRO / RIDE6 | HTTP:80 | `/api/` | REST，`Ride3ProApiResponse<T>` 包裹；**客户端自设三层串行**（L1 `Ride3ProRequestScheduler` 优先级队列 + 单 worker = 主路径；L2 `Ride3ProHttpRequestQueue` Mutex 兜底；L3 `Ride3ProHttpSerialDispatcher` `maxRequests=1` **只服务 Glide**）+ `retryOnConnectionFailure(false)`。⚠️「设备不接受并发」静态无证据 |
| M3 | HTTP:80 + **TCP 推送** | `/app/` | 泛化 `param` 协议 + 设备单向 JSON 推送 |
| RIDE5 | HTTP:80 | `/cgi-bin/hisnet/` | CGI，响应是**裸文本**不是 JSON |

**Ride3Pro/Ride6 端点**（`ride3pro/Ride3ProApiService.java`）：鉴权 `GET /api/authdevice?seed=<long>`（`/api/rtspstatus?seed=<long>` **只声明、零业务调用点**，不算鉴权步骤）；设备 `device/status`、`device/info`、`reboot`；拍摄 `capture`（**同样只声明无调用点**，官方「拍照」是播放器截 RTSP 帧，`DeviceDetailActivity.java:1202-1240`）、`record/start|stop`、`setmode?mode=`；设置 `menu/xml`、`menu/getparameter?id=`、`menu/setparameter?id=&value=`；回放 `playback/dayinfo?date=`、`filecount`、`filelist?mode=&file_index=`、`thumbnail?file_index=`、`rawdata`、`start|pause|stop|delete|settime|setspeed`；存储 `sd/info`、`system/formatsd`；时间 `vendor/send-time?year&month&day&hour&minute&second`；固件 `POST /api/firmware/upload?md5sum=&model=&hw=&sw=`。

**M3 HTTP 端点全表**（`m3/M3ApiService.java:47-134`，全部 `@GET`，前缀 `/app/`）：
`deletefile?file=` · `getparamitems?param=` · `getparamvalue?param=` · `getbatteryinfo` · `getcurmode` · `getdeviceattr` · `getfilelist` · `getgravitydirection` · `getmediainfo` · `getproductinfo` · `getrecduration` · `getsdinfo` · `getthumbnail?file=` · `reset` · `sdformat` · `setting?param=` · `mode?param=` · `setparamvalue?param=&value=` · `playback?param=` · `setsystime?date=` · `settimezone?` · `setwifi?wifissid=&wifipwd=` · `downloadFile(@Url)` · `POST /upload/{savepath}/{filesize}`

**M3 TCP 推送通道 —— 三个反直觉事实（会直接影响我们的实现）**：
1. **没有帧分隔符。** 线上解码器是 `LegacyReadChunkFrameDecoder`——「一次 read 到一个非空 chunk 就是一帧」（`LegacyReadChunkFrameDecoder.java:18-21`，`reset()` 是空实现）；活解码器由 `M3DeviceAdapter.java:103`（默认实参）→ `:110-121`（方法引用 `M3FrameDecoderKt.createDefaultM3FrameDecoder`）→ `M3FrameDecoderKt.java:10-12` 确定。`DelimitedFrameDecoder` 与 `UnconfiguredFrameDecoder` **都是零构造点的死类**，分隔符字节在整个语料里从未被赋值（`DelimitedFrameDecoder.java:20,30,31`，默认 maxFrame 64KB / maxBuffer 256KB —— **运行时不生效**）。单次读上限是 `maxReadBytes = 4096`（`DefaultM3SocketConnector.java:86`）。副作用：跨 read 的长 JSON 会被切成两帧，第二帧进 `Unknown`。
2. **端口不是常量**，从 `/app/getmediainfo` 响应里解析（`M3DynamicEndpointPolicy.java:59-62`、`:78`，调用链在 `M3DeviceAdapter.java:920-922`），校验 `1 ≤ port < 65536` 且无默认值——非法端口整个 open 直接失败，host 强制等于控制 host。
3. **单向推送，App 从不往这个 socket 写请求**：`SessionSocket` 实现跨 `DefaultM3SocketConnector.java:343-409`，但接口 `M3SessionSocket.java:12-18` 只有 `getFailures`/`getMessages`/`isOpen`/`close`，且全 `core/device/` + `data/source/socket/` 目录 `getOutputStream` **零命中**；无心跳/保活。连不上时只把 `M3_SOCKET_EVENTS` 从能力集去掉，会话照建（`M3DeviceAdapter.java:311-322`、`:332-338`）。

推送报文（UTF-8，trim 后单个 JSON 对象，`M3JsonMessageDecoder.java`）：信封 = 顶层 `msgid`(string) + 顶层 `info`(object) + **顶层第三个键的字面量静态不可证**（jadx 把它折叠成了 `DeepLinkPresetEvent.UMEventParamTime`，该类不在反编译产物里；按 Umeng 埋点惯例**疑为** `"time"`、类型 long，**不是 CONFIRMED**）。两个边界：**空帧 → `decode` 直接 `return null`**（既不产消息也不报错，`:33-37`）；**非法/半截 JSON → `Unknown(原始串)`，不上抛**（`:125-131`）。

| `battery` | `capacity`,`charge`（默认 0） | 电量 | 有 |
| `rec` | `value`（`==1` 录制中） | 录制状态 | 有 |
| `rec_time` | `recConsumTime`,`recFileTime` | 录制时长 | 有 |

**RTSP 预览**：R3Pro/R6 = `rtsp://<host>:8080/?action=stream`；M3 = 从 `getmediainfo` 返回的 URI 解析（scheme 必须 rtsp、**禁止 userinfo 凭据**、缺省端口 554、host 强制同控制端）；Ride5 = `rtsp://<host>:554/livestream/1`——⚠️ 端口**不来自设备属性**：`RTSP_LIVE_PORT` 是客户端 `companion object` 常量（554），先写进 `EndpointGrant`，起流时再由 `Ride5DeviceMediaPort.java:105-110` 从 grant 的 `allowedPorts.singleOrNull()` 取出来拼 URL；**设备不参与协商**，Ride5 的 CGI 里没有任何端口字段。

**seed 握手**：`seed = kotlin.random.Random.nextLong(Long.MAX_VALUE)` 的**明文非负 Long，无哈希无签名**（`Ride3ProPlaybackRepositoryImpl.java:1049`、`Ride3ProStreamRepositoryImpl.java:239`）。实际顺序：**设备认证（`authdevice`，`result` 非 0 且非 -2 才算失败）→ 同步设备时间（`vendor/send-time`，失败仅 `Timber.w`）→ `markReady` → 切换预览模式（`setmode?mode=0`，失败硬抛）→ 起播**（`Ride3ProStreamRepositoryImpl.java:239-267`、`:307-321`、`:380-392`）。UI 只有三个步骤串（`ride3pro_preview_step_device_auth` / `_switch_mode` / `_sync_time`），**不存在 rtspstatus 步骤**。「seed 让相机 RTSP 服务端授权本次连接」是**推断**：客户端没有任何把 seed 交给播放器的通路，RTSP URL 不含 seed，auth 响应的 `info` 声明为 `Any?` 且不解析。握手缓存 `Ride3ProPreviewHandshakeCache` 以 `(deviceIdentity, sessionId, routeRevision)` 为键，`consume()` 是**只读探测（peek）**：命中且未过期时 `return true` **不删除**，只有过期分支才 `remove`（`:199-211`），有效期 `VALIDITY_DURATION_MS = 600000`（**10 分钟**，单调时钟 `System.nanoTime()/1e6`）→ 预览与回放各自都能复用同一次握手。**复现成「一次性」会让每次起流多打一次 auth + send-time。**

**能力集（`DeviceCapabilities.names: Set<String>`）**：
- M3：`M3_HTTP_CONTROL`、`M3_MEDIA_ENDPOINT`、`M3_SOCKET_EVENTS`
- RIDE5：`RIDE5_HTTP_CGI`、`RIDE5_CALLBACK_9002`、`RIDE5_RTSP_LIVE`
- RIDE3PRO/RIDE6：**运行时拼接** `"<typeCode>_HTTP_CONTROL" | "_STATUS" | "_RTSP_PREVIEW"` → 实际是 `R3Pro_*` / `R6_*`（`Ride3ProDeviceAdapterSession.java:384-388`）。⚠️ interop 端不能写死，必须复刻拼接规则。

### 1.5 设置项

**结构结论（限定范围）**：Ride3Pro/Ride6 的**取值集合**（`<Value>` 列表）确实不在 APK 里，必须运行时向设备取；但「**哪些项存在**、**哪些项可写**、**分区顺序**、**英文→中文映射**」这四张表 APK 里是**写死可枚举**的。M3 的参数名表（22 键）与 Ride5 的 `-type` 词表更是**完全静态**，不受该结论约束。

**(a) Ride3Pro/Ride6 —— 设备下发菜单 XML**（文件名 `WIFI_MENU.xml`，客户端硬拒 `<!DOCTYPE`，`Ride3ProMenuXmlParser.java:33-35`）。⚠️ **取菜单的通道不是 HTTP**：`GET /api/menu/xml` 只是接口声明与「无会话 executor」时的兜底路径，有会话时官方把同一个 `getMenuXml` 改写成**裸 socket** 读同一份菜单（`Ride3ProSessionApiService.java:1498-1520` → `Ride3ProSessionTransport.java:373-380` → `readMenuXmlRaw`，`:538-543` jadx 反编译失败但局部名含 `socket`；建连用 `MENU_CONNECT_TIMEOUT_MILLIS`，`:657`），数值上限四个常量均 `@Deprecated` 且仍是活路径：`5000` / `524288` / `8192` / `30000`（`:65-74`）；**socket 上到底写什么请求静态无解**。Schema 全是**子元素、无属性**，解析器只读这 6 个名字：

```
<Category>            任意深度，文档序
├── <Name>            分区显示名
└── <Setting>         仅直接子元素，有序
    ├── <Name>        设置项显示名
    ├── <ID>          不作请求 id，但被兼容策略**数值化比较**用来认项（见下）
    ├── <Type>        原文自由字符串，客户端按整数解析（见下）
    ├── <Default>     默认值（不是「当前值」）
    └── <Value>*      仅直接子元素
        ├── <Name>    选项显示名
        └── <ID>      选项值
```

- **`<Type>` 被 `ride3ProSettingTypeCode()` 宽容解析成整数**（`0x` 前缀按 16 进制、否则 10 进制，`Ride3ProSettingsRuntimeMapperKt.java:17-35`），驱动 5 种渲染分支（`Ride3ProSettingsRuntimeMapper.java:53-94`）：`0`/`3` = 按 `<Value>` 反查选中项、`1`/`4` = 动作项（label `Execute`，且**单独再发一次 `getparameter?id=<requestId>`**，`Ride6SettingsProtocolClient.java:361,390,449` 的 `setOf(1, 4)`）、`2` = 原值直显；解析不出来时退回「原值 → `<Default>` → 空串」。
- **当前值不在 XML 里**：先 `getparameter?id=all` 批量读，再对 `Type ∈ {1,4}` 的项逐条补读。
- ⚠️ 但**不能读成「客户端完全不用 `<ID>`」**：`Ride6SettingsCompatibilityPolicy` 把 `<ID>` 做**数值化比较**来识别两项——`isFactoryReset` = `requestId=="factory_reset"` **或** id 数值 == `0x0000208`（`:17,:41-44`）、`isWifiPassword` = `requestId=="wifi_passwd"` **或** name==`Password` **或** id 数值 == `0x0000301`（`:19,:36-39`）；`factory_reset` 成功后还会把缓存的 WiFi 密码复位（`:46-56`）。

**没有** min/max/step、没有只读位、没有隐藏位——这些都在 App 侧策略类里（`Ride3ProSettingsMenuPolicy`、`Ride6SettingsCompatibilityPolicy`、`Ride6SettingsLocalizer`）。

### 1.6 文件下载与断点续传

- 回放条目以**整数 `file_index`** 为主键（不是文件名）：`filelist?mode=&file_index=` → `thumbnail?file_index=` / `rawdata` / `start` / `delete`。
- ⚠️ **设备侧下载不用 HTTP `Range`。** `ResumePolicy` 四态：`Disabled` / `HttpRange` / `DeviceOffset` / `DeviceQueryOffset`；其中 `HttpRange` **显式只允许 Internet 源**（云/OTA），设备源必须走 `DeviceOffset`（`ResumePolicyRegistry.java:25-55`）。
- 该结论的**三条硬证据**（此前只有策略表、没有线上证据）：① `TransferRequest.java:163-164` 对设备传输使用 `ResumePolicy.HttpRange` 时直接 `throw IllegalArgumentException("Device transfer requires an explicit device offset policy")`；② 全语料里字面 `"Range"` 只出现 1 处，且是日志脱敏白名单（`DiagnosticHttpLogPolicy.java:134`），`StreamingTransferEngine.java:1019` 读的是响应头 `Content-Range`；③ 设备下载的请求构造 `DownloadFileExecution.java:123` 是 `new Request.Builder().url(strWithOffset).build()`——**不加任何 header**，续传位置只拼进 URL。
- 设备续传的真实线上形态是 **query 参数**：`GET /api/playback/rawdata?...&offset=<bytes>`（`Ride3ProPlaybackDownloadResumePolicy.java:233-238`）。
- **续传受固件门限**：低于 `v1.20260708.101448` 直接拒绝并记 `reason=legacy_firmware`（`DownloadUtil.java:1602-1606`）。
- 恢复前置条件：`checkpoint.offset > 0` 且 `== 本地文件长度` 且 `sourceFingerprint` 匹配；响应 `Content-Length` 表示**剩余字节**而非全文件（`DownloadFileExecution.java:202`）；重试上限 5。

### 2.4 通讯方式

**(a) Ambarella（`type` = `H75N`/`CV75`）—— 裸 JSON over TCP**

- TCP `<ip>:7878`，`connect(…,5000)`，命令 `soTimeout=5000`，轮询未决数据时降到 **10ms**。
- **请求 = 原始 Gson JSON 字节，无分隔符、无长度前缀、无换行**（`outputStream.write(str.getBytes())`），例：`{"msg_id":268435463,"token":123,"workmode":"System","name":"Resolution","value":"4K30"}`。

## 3. idGoLive（APK 包 `com.id221.golive`，Java 命名空间 `com.icatch.golive`）

> ⚠️ 包名易错点：`AndroidManifest.xml:7` 的 package 是 **`com.id221.golive`**（FileProvider authority 也跟着它），而所有 Java 类在 **`com.icatch.golive`** 命名空间下。两者不一致，别只记一个。

### 3.2 识别方式

- **不存在 SSID 白名单/前缀集/正则**（已按 `SSID_PREFIX`、对 SSID 变量的 `startsWith`/`contains`、形似 SSID 的字面量全量搜索确认缺失）。仅有的两个 pattern 是刻意宽松的 `PatternMatcher`（type 3 = `PATTERN_PREFIX`）用于 WifiSpecifier，**不是识别器**：`"[\u4E00-\u9FA5a-zA-z0-9@_-]+.*"`（任意中文/字母/数字/`@_-`）与 `"[a-zA-z0-9@]+.*"`。
- 设备的"身份"就是**手机当前连着的 SSID 原文**（`MWifiManager.getSsid()` 去引号后直接当显示名，兜底字面量 `"unknown"`）。
- **mDNS/NSD：完全没有**（无 `NsdManager`、无 `_http._tcp`、清单无 `<tech-list>`）。
- **蓝牙**：设备名判定是**精确等值单个全局名** `getName().equals("iCatchBT")`（`ICatchBluetoothAssist.java:130`）；SPP/RFCOMM UUID `00001101-0000-1000-8000-00805F9B34FB`；iCatch BLE 特征 `e44b82fb-f3a6-4c72-ab3f-bf94abfd9930`（读写同一个）；HM-10 兜底特征 `0000ffe1-…`；CCCD `00002902-…`。**不声明 service UUID**，靠遍历 `getServices()/getCharacteristics()` 字符串匹配。BLE 与 SPP 由全局 `AppInfo.isBLE` 切换。
- **MAC/OUI 规则：未找到。**
- **USB**：代码常量 `USBHost_Feature.java:28,32` 是 `USB_VENDOR_ID = 10925`（= **`0x2AAD`**，旧版此处写 `0x2A0D` 是错的）/ `USB_PRODUCT_ID = 25427`（`0x6353`），另可比 deviceClass/subclass/protocol。**清单侧唯一带字面 VID/PID 的「机型表」是 `res/xml/device_filter.xml`（只有 2 条 `<usb-device>`）**：`vendor-id="10925"`+`product-id="25859"`(`0x2AAD:0x6503`)、`vendor-id="16716"`+`product-id="25971"`(`0x414C:0x6573`)。⇒ **VID 一致、PID 与代码常量不一致**，白名单以 `device_filter.xml` 为准，`USBHost_Feature` 的两个常量是另一条匹配路径。
- **确认设备的探测链（CONFIRMED，顺序）**：并发两个 ICMP `ping -c 3 -w 3`（`ConnectDeviceManager.java:266`）打 `192.168.1.254` 与 `192.168.169.1`；ping 只是可达性闸门，**真正确认靠各 handler 的 `getSSID()`**：

| Handler | 确认请求 | 响应解析 |
|---|---|---|
| `LyIC` | `http://192.168.1.254/?custom=1&cmd=3029` | **XML**，取 tag `SSID`、`PASSPHRASE` |
| `QzIC` | `http://192.168.169.1/app/getdeviceattr` | **JSON** `info.ssid` |
| `LyCmdWithYzIC` | `http://192.168.1.254/app/getdeviceattr` | JSON `info.ssid`，空则回落 `LyIC` |

  另有第二条非 HTTP 探测：`LySocketClient().connectAndReceive("192.168.1.254", 3333)` —— 这是 App 自有代码里**唯一的端口字面量**。
- 型号串载体：SDK 路径 `CameraFixedInfo.getCameraName()`；HTTP 路径 `/app/getproductinfo`（具体 JSON key 未确认）；云端固件表字段 `product,name,region,version,download`。

### 3.3 连接方式

- **拓扑固定：相机 = AP，手机 = STA。没有 Wi-Fi Direct**（`WifiP2p` 零命中）、**没有扫码配网**、没有 NFC、活路径里没有 `WifiNetworkSuggestion`。
- ⚠️ 「无扫码」要说准：包里**有** zxing 与两套 QR 生成类（`com/icatch/golive/utils/QRCode.java:18-81`、`com/icatchtek/baseutil/qrcode/{QRCode,SetupQRCode}.java`），但 `QRCode` 只被用在**分享链接生成二维码**上（`PreviewPresenter.java:1918` 的 `shared_url_qrcode`），全树**没有任何 QR 解码入口**（`QRCodeReader`/`DecodeHintType` 在 `com/icatch*/` 下零命中），`SetupQRCode` 也无包外调用者 ⇒ 「无扫码**配网**」成立，而不是「无二维码」。
- **配网/连接入口 = WiFi 自动连接 / WiFi 手动 / USB / 蓝牙** 四条（`AddNewCamFragment`）；此外还有两条**不走 `AddNewCamFragment` 的旁路**：①组播 AES 配网 `simpleConfig`（§3.6），②**手机开热点让相机连**（`WifiApActivity` + `activity_wifi_ap.xml:24,50` 的默认 `test01` / `1234567890` 与 no/wpa/wpa2 三态）。⇒ 精确表述：**无 QR，有 BT 配网 + 组播配网 + OS 级直连 + 手机热点四条替代路径**。
- **路径 A（Android 10+，`wifi_auto_connect`）**：`WifiNetworkSpecifier` + `setSsidPattern(宽松 glob)` + `setWpa2Passphrase`，**用户只输密码、从不选 SSID**，密码框预填 `AppInfo.default_pwd = "1234567890"`（注意与 TUWIN/XTU 的 `12345678` 不同，是 10 位）。关键在 `onAvailable → cm.bindProcessToNetwork(network)`（`WifiNetworkSpecifierUtil.java:139`），因此 `ApiCaller` 必须把 OkHttp 走 `PanoramaApp.getContext().getWifiNetwork().getSocketFactory()`（`ApiCaller.java:148`）。错误码：`onUnavailable→onError(0)`、`onPasswordError→onError(-1)`（触发重填密码对话框）。
- **路径 B（老式 `WifiManager.addNetwork` + `enableNetwork`，`WifiCheck.java:216,218`）**：只被**蓝牙配对流程**使用；Android 10+ 上是 no-op ⇒ 整个 BT 配网路径实际只在 API 28–29 可用（与清单缺 `BLUETOOTH_CONNECT` 一致）。
- **蓝牙配网载荷字段（你要的 spec）**：`ICatchWifiInformation.getWifiSSID()` / `getWifiPassword()` / `getWifiEncType()`（int，选 WEP/WPA/无），取自 `AppInfo.iCatchBluetoothClient.getSystemControl().getWifiInformation()`；同通道还有 `getSystemControl().enableWifi()` 唤醒相机的 AP。连上后轮询 `wifiCheck.isWifiConnected(ssid)`，15 次超时。
- **端到端顺序**：选入口 → (可选 BT 前置：扫→验 `iCatchBT`→连→`enableWifi()`→拿 ssid/pwd/encType→`addNetwork`→轮询) → WiFi join（A 或 B）→ `CameraManager.createCamera(WIFI_CAMERA, ssid, ip, …)` → `MyCamera.connect()`：由当前 WifiInfo 反算本机地址 `WifiAPUtil.getLocalIPAddressFromWifiInfo()` 并构造 `ICatchINETTransport(ipAddress, localIpAddress)` → `prepareTransport()` → `commandSession.prepareSession(transport, enablePTPIP)` + `panoramaSession.prepareSession(transport)` → **SDK 失败则回落** `ConnectDeviceManager.initDevice()` 的 HTTP IC 路径 → 连上后按 `hasFuction(CAMERA_DATE_TIMEZONE/CAMERA_DATE)` 对时 → `startHeartbeatPackage()`（**周期按 handler 分档**：无 handler 兜底 30000 ms（`ConnectDeviceManager.java:205`）、`LyIC` 10000 ms（`LyIC.java:225`）、`QzIC`/`LyCmdWithYzIC` 4000 ms（`QzIC.java:239`、`LyCmdWithYzIC.java:188`））。
- **明文流量全局放行**：`network_security_config.xml` 里 `cleartextTrafficPermitted="true"`。

### 3.6 鉴权、心跳与固件升级

- **发现**：`CommandSession.startDeviceScan()` → 原生扫描 + UDP 组播 `234.168.168.168:5002`；命中通过事件 `DEVICE_SCAN_ADD=85` 上报。⚠️ **组播有两套实现**：Java 侧 `CoreMulticast`（`prepare()/receive()`，**只收**，用于发现）与 native 侧 `simpleconfig`（**收+发**，是配网协议，见下条）。⚠️ 清单里声明的是拼错的 `CHANGE_WIFI_MULTICAST_STAT`（少尾字母 `E`，`AndroidManifest.xml:39`），真正的 `CHANGE_WIFI_MULTICAST_STATE` **从未声明**，而 SDK 会 `createMulticastLock("multicast.test").acquire()`（`CoreMulticast.java:21-22`）⇒ 该锁是否真生效**静态不可证**（Android 的 `MulticastLock` 一般要求 `CHANGE_WIFI_MULTICAST_STATE`），组播发现在真机上可能压根不通，见 §6。
- **IC 判定的失败计数是共享的**：两个独立 ping 共用一个 `failure_connect_count`，累到 2 就发 `404`（`ConnectDeviceManager.java:28,57,71`）——一个 bug，别照抄。成功判据是 HTTP JSON `code==200` 且 `data.area_support` 存在。
- **配网密钥硬编码（组播 `simpleConfig` 通道）**：`simpleConfig(ctx, essid, pwd, ip, gw)` 默认 `timeoutSec=180`（`ICatchCameraAssistImpl.java:222-223`），不传 key 的重载直接套 `__default_key`（`:227-228`）；key 是 16 字节有符号字面量 `{33,126,26,22,40,-34,-46,-89,-85,-25,-123,-120,9,-54,128,60}` = `21 7E 1A 16 28 DE CE A7 AB E7 85 88 09 CA 80 3C`（`:41`），收包轮询 sleep **50 ms**（`:74`）。⇒ 这是一条**独立于连接流程的配网通道**（AES-CBC-128 在 native）。
- **鉴权**：HTTP 通道**完全没有**（无 Authorization/Cookie/token/nonce，按缺失确证，`ApiCaller.java:95-137`）——AP 网段内任意设备可被完全控制。PTP 会话 `prepareSession(sessionID, ip, "", "")` 传两个空串，即 SDK 留了凭据槽但未用（`ICatchCameraSession.java:91`）。
- **心跳**：HTTP `cmd=8888`、`cmd=3016`、`/app/getparamvalue?param=rec`、`api/setdeviceinfo/?custom=1&cmd=4016&par=1`；周期 = `ic.getHeartbeatPeriod()` —— **`LyIC` 10000 ms（`LyIC.java:225`）/ `QzIC` 与 `LyCmdWithYzIC` 4000 ms（`QzIC.java:239`、`LyCmdWithYzIC.java:188`）/ 无 handler 兜底 30000 ms（`ConnectDeviceManager.java:205`）。链路健康另由 `setConnectionCheckParam(connectionCheckTimes=4, connectionCheckInterval=4, 0)` 驱动（`AppInfo.java:57-58`、`CommandSession.java:120`）；⚠️ **第三个实参在 SDK 里被丢弃**——`setConnectionCheckParam(int i, double d, int i2)` 把 `i2` 又传成了 `i`（`ICatchCameraConfigImpl.java:84-85`），别继承这个 bug。
- **固件升级**：`updateFw(session, path)` 原生；App 把文件命名为 **`SPHOST.BRN`** 放到设备上 **`/idGoLive/Resoure/`**（拼写如此），再 `notifyUpdateFw()`，靠事件 96–100 回报。云端固件清单来自 `https://idcam.oss-cn-shenzhen.aliyuncs.com/Firmware/firmware.json`，字段 `product,name,region,version,download`。
- **现代权限全缺**：无 `BLUETOOTH_SCAN`/`BLUETOOTH_CONNECT`、无 `NEARBY_WIFI_DEVICES`、无 `FOREGROUND_SERVICE`、无 `POST_NOTIFICATIONS`，但 `targetSdk=35` ⇒ 蓝牙配对流程在 Android 12+ 上是坏的（推断，依据是清单只声明了 legacy `BLUETOOTH`/`BLUETOOTH_ADMIN`）。`minSdk=28`。

### 3.7 实时预览

**主相机（PTP 路径）不是 RTSP 也不是 MJPEG-over-HTTP**，而是同一 PTP 会话内的原生拉流：`ICatchIPancamPreview.start(ICatchStreamParam[, audio][, streamNo])` / `.stop()` / `.isStreamingOn()` / `getStreamControl()/getStreamPublish()/getThumbnail(...)`（`pancam/customer/ICatchIPancamPreview.java:20-44`）。
参数串即编解码协商：`H264?W=&H=&FPS=&BR=`（codec=41，默认 1920×960@30）、`MJPG?W=&H=&Q=&BR=`（codec=64，默认 q=50）、JPEG（codec=64）；帧在 App 侧由 `H264DecoderThread` / `MjpgDecoderThread` 解码。⚠️ **这些串是固件返回的、不是 APK 里的字面量**（20 个 arm64 `.so` 全量搜 `H264?` 零命中），App 解析后还会**改写帧率**（`StreamInfoConvert.java:8-34` 兜底 fps=30；`ConvertTools.java:80-95` 按高度降到 720→15、1080→10，详见 §3.4 分帧小节）。
握手顺序：`prepareCommandSession()` → `getPlaybackClient()/getControlClient()` → `changePreviewMode(int)` → `start(param)`；能力门 = `SUPPORT_PREVIEW` **55295（`0xD7FF`，旧版误写 `0xD7DF`）**（`CameraProperties.java:1379`）。
**拉流的实际 socket/端口在原生层，Java 与 .so 字符串里都找不到。**

**记录仪/副机走 RTSP，无鉴权**：默认 `rtsp://192.168.1.254`，Qz 系 `rtsp://192.168.169.1`；且**必须先 HTTP `?custom=1&cmd=2015&par=1` 打开预览**，`par=0` 关闭（`RequestInfo.java:44-45`、`LyIC.ready2CamLive:332-344`）。⚠️ **三个 IC 类返回的是裸 `rtsp://<ip>`——无路径、无端口**（`LyIC.java:168,220`、`QzIC.java:165,234`、`LyCmdWithYzIC.java:164,183`），`ic == null` 时兜底也是 `rtsp://192.168.1.254`（`ConnectDeviceManager.java:173,199`）⇒ **路径由播放器侧补，官方代码里没有完整 URL**，列为 §3.9 待抓包项。远端文件回放另拼一次：`"rtsp://192.168.1.1" + filePath`（`RemoteDeviceFilesFragmentPresenter.java:308`）。

### 3.8 文件传输

- **PTP**：`getFileCount()` / `listFiles(filter[,start,count])` / `setFileListAttribute(...)`，分页受能力位 `NEW_PAGINATION_GET_FILE=2` 控制；条目 = `ICatchFile`（`fileType`：**1=照片,2=视频**，由 `PbDownloadManager.java:127-129` 分支确证）；`getThumbnail(ICatchFile)→ICatchFrameBuffer`、`getQuickview(ICatchFile)`（原生 `ptp_mtp_getobjectquickview`）；专用批量通道 `openFileTransChannel()/closeFileTransChannel()/cancelFileDownload()`。设备路径形如 `A:/DCIM/100GOPRO/…`。
- **HTTP 映射**：`FileInfo.java:40-43` 把 `A:` 前缀直接替换成 `http://192.168.1.254`；反斜杠路径则 `furl = "http://192.168.1.254/Novatek/" + <父目录> + "/" + <文件>`，`turl = furl + "?custom=1&cmd=4002"`（`:53-55`）；`/app/` 系 `turl = <host> + "/app/getthumbnail?file=" + path`。
- **断点续传：有，标准 HTTP `Range`** —— `header("RANGE", "bytes=" + mAlreadyDownLength + "-")`，GET 与 POST 续传都带（`OkHttpDownUtil.java:119,242`；header 名是**大写 `RANGE`**，HTTP 头大小写不敏感 ⇒ 无功能影响，但 `:242` 把 Range 挂在 POST 上服务端多半会忽略），首次是普通 GET/POST，重试改派到 "Renewal" 变体（`:308-319`）。
- **PTP 侧还有一条独立的续传机制**：native `libcontrol.so` 导出 `ptp_getpartialobject`（arm64 与 armeabi-v7a 两个 ABI 都有，`_work/re/idgolive/natives-symbols.tsv:7301`）⇒ 设备源续传语义**不止 HTTP 一种**，插件层要按 profile 选。
  ⚠️ 这与 TUWIN（禁用 Range、用 `?offset=`）和 XTU（只有 Ambarella 支持 offset）**三家三种续传语义**，必须做成能力开关。

## 4. 对自研插件层的硬约束

1. **以探测结果路由，不以型号名路由。** XTU 根本没有「型号→协议」表，分派键是设备自报的 `type`；TUWIN 的 `RIDE5.expectedModels` 是空集。所以 `CameraProfile` 的匹配条件必须是 **(SSID 模式 ∧ 探测端点命中 ∧ 响应字段谓词)**，型号名只作为展示与统计维度。
2. **传输层至少六种**：HTTP-REST(JSON)、HTTP-CGI(`var K="V";` 文本)、裸 JSON-over-TCP(无长度前缀，靠"能否解析成 JSON"分帧)、二进制定长帧(72B/200B 小端)、**PTP container over TCP/IP 与 PTP over USB（UVC bulk / UVC isoc / MSC-SCSI 三种传输）**、**UDP 组播（发现 + AES 配网）**。外加 RTSP、RTMP 上行，与「设备回拨手机」的反向 socket（XTU 的 5678 由 `HisiSocketServer` 监听，**海思与 SigmaStar 共用**）。
3. **分帧策略要可插拔**：TUWIN M3 用 read-chunk-as-frame，XTU Ambarella 用 valid-JSON-accumulation，XTU 8080 用定长头。写死任一种都会在某品牌上崩。
4. **设置项必须走「设备自描述 + 运行时枚举」**，且要能承载三种发现协议：菜单 XML（TUWIN R3Pro/R6）、`primarymenuitem/secondmenuitem` CSV（XTU）、`getcapability(workmode,type)` 矩阵（老海思）、`getparamitems?param=all_<mode>`（M3）。UI 类型靠「选项数 ≤2 且值为 ON/OFF ⇒ 开关」这类启发式推断。
5. **参数键跨品牌不通用**，且同品牌内也不统一（`record_resolution` vs `rec_resolution` vs `Resolution`；`wifi_passwd` vs `wifipwd` vs `-wifikey`）。内部规范名 + 每 profile 一张映射表，别指望一个 key 空间。
6. **Ride5 的 CGI query key 带字面前导 `-`**，Retrofit/HttpUrl 之类会保留但很多 builder 会丢；必须用能原样输出 key 的构造器。
7. **TUWIN 的 `id` 是从菜单名推导的**（`normalize()` + 查表），不是 XML 里的 `<ID>`。复刻错这张表 → 所有 setparameter 静默失效。
8. **能力名对 R3Pro/R6 是拼接出来的**（`<code>_HTTP_CONTROL` 等），不能写死字符串。
9. **续传语义分裂**：TUWIN 设备源用 `?offset=` 且受固件版本门限、明确禁用 `Range`；XTU 只有 Ambarella 支持 offset 续传，CGI 家族完全没有。**默认按「不支持续传」实现，能力开关打开。**
10. **Ambarella 取缩略图/文件前必须先发 `261 set_clnt_info`**，否则设备不认后续 8787 数据连接。
11. **命名陷阱清单**：`XTU S7PRO`/`XTU S7PRO MAX` 带空格而其余不带；Amba 上报名要 `split("-")[0]`；`var capacity=` 这个键名自带尾随 `=`；CSV 里 `,,` 要先变成 `,-,` 再解释为空；idGoLive 协议里 `mineType` 拼错、`DEFALUT_TO_PREVIEW` 拼错、固件目录 `/idGoLive/Resoure/` 拼错 —— **照抄字面量，不要"顺手改正"**。
12. **命令层要能表达 PTP 模型**：idGoLive 的主相机是「设备属性表（16 位 DPC + 子属性索引，int/string/bytes 三型）+ 对象表（handle + ObjectInfoPropList）+ 事件队列」。所以 `CameraProtocol` 不能只有 `send(command, params)`，必须再支持 `getProperty(id, type)` / `setProperty(id, value)` / `listObjects(filter, page)` / `events(): Flow<Event>` 这一组原语，否则 iCatch 系接不进来。
13. **一条命令通道 ≠ 一个设备**。idGoLive 一台设备上并存 **11 条**通道（PTP/IP 控制+文件、PTP over USB ×3、HTTP `?custom=1&cmd=`、`/app/`+`/api/` JSON、XML-TCP:3333、UDP 组播发现+配网、BLE/SPP、RTSP、RTMP 上行；另有一条 `enableSocketIO` 是 SDK 提供但 App 未接的**第 12 条**），XTU 的 Ambarella 是「7878 命令 + 8787 数据」双 socket，海思/SigmaStar 还有 8080 二进制帧与 5678 回拨。插件的会话对象要允许**多路并发连接、各自独立分帧与生命周期**。
14. **安全上不能假设任何鉴权**。idGoLive 的 HTTP 通道零鉴权（按缺失确证），XTU 的 CGI 也是明文无 token，只有 TUWIN 有 `seed` 握手（且 seed 是明文随机数、无校验）。我们连上相机 AP 后就是全权控制；反过来说，**任何"设备已认证"的乐观假设都是错的**，UI 上要把"当前连的是哪台/哪个 IP"显示清楚。
15. **别把"厂商 App 有型号表"当成前提，但也别当成完全没有。** idGoLive 是 iCatch 的白标公版 App：**没有「机型 → 能力」注册表**（`CameraType`/`CameraAddType` 无品牌、无芯片枚举），但**有**一条 33 项的「相机名 → 跳过写时区」黑名单（`CameraProperties.java:1476`，命中即 `:1480` `return false`，不写 `0xD83E`）。选 handler 也**不是**「对三个 IP 并发 ping」：ping 只打 `192.168.1.254` 与 `192.168.169.1`（`ConnectDeviceManager.java:266`），**`192.168.1.1` 的 PTP 机不参与 ping**，由 `MyCamera.connect(true)` 的成败决定；两路 ping 还**共享一个失败计数器**（`:33-37`，累到 2 就整体 404）。⇒ 准确的模型是**四层判定**：PTP 会话成败 → ICMP 应答者 → `getSSID()` 成败 → 相机名黑名单。我们做「型号 → Profile」是比官方更好的设计，但要留一条**「无型号、纯探测」的兜底路由**，且 profile 里要有「按设备名跳过单条命令」这一层，否则遇到 idGoLive 这类贴牌长尾就接不进去。
16. **命令兼容性黑名单要能表达**：同一协议下，某些型号要跳过/改写个别命令（idGoLive 按 `getCameraName()` 与 33 项名单**全等比对**跳过写 `0xD83E` 时区，注意不是前缀匹配；XTU 按 `name endsWith "S7PRO"` 改 `record?-cmd=Storie`；TUWIN 按固件版本门限决定能否续传）。Profile 结构里要有 `命令级 override / 门限` 这一层，不能只有"支持哪些命令"的粗粒度能力集。
