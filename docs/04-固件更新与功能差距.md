# 固件更新（OTA）与功能差距

> 数据来源：三个官方 APK 的静态逆向，结论标 `path:line`；CONFIRMED = 读到代码，INFERRED = 从命名/上下文推断，未找到 = 搜过且不存在。
> 分析日期 2026-09-20。协议/型号基础事实见 [03-品牌型号与协议矩阵](03-品牌型号与协议矩阵.md)。
> 目的：(1) 把三家「相机固件更新」的实现机制与线上契约挖清楚，作为我们 clean-room 重实现的依据；(2) 盘出我们 App 相比官方的功能缺口并排优先级。

## 0. 结论先行

> 本节是地图。§1–§3 三家机制，§4 横向对比，**§5 本次下载真实固件后的镜像实测**，**§6 变砖风险审计与我们必须自建的护栏**，§7 我们自己的差距与落地顺序。
> ⚠️ 本文早先版本有 4 条结论被更深的审计推翻（下方标「更正」），§5.5 另列了镜像实测对前文的 5 条修正。

1. **固件更新不是一个功能，是「云检版 + 下载 + 送包 + 相机自己烧」四段。** 前两段三家形状接近，后两段完全不通用：XTU 一个 APK 里并存 4 条送包通道 + 3 代云接口，idGoLive 把送包整条塞进 native 的 FTP，TUWIN 三条通道各一套。所以插件层必须把 OTA 做成**按 profile 分派**的能力。
2. ⚠️ **更正**：「只有 TUWIN 闭环了装机后回读版本」是**错的**。TUWIN 的版本回读只存在于 `core.update.DeviceOtaCoordinator`，而该类**只在 DI 里被构造、从未被调用**；现役 `UpgradeHelper` + `UpgradeActivity` 路径在上传 POST 返回后弹一个 30 秒倒计时，然后**宣告成功并离开**，零回读。⇒ **三家 App 全都没有装机后版本确认；变砖在官方阵营里不可检测。**
3. ⚠️ **更正**：XTU 的四条送包通道**只有一条是活的**。审计确认 `UpgradeFirmwareActivity` 无 manifest 条目（点开即 `ActivityNotFoundException`）、`UpgradeSendFirmActivity` 无人 `startActivity`、`SendSoftActivity` 三个静态字段从未赋值、`CURRENT_APP_TYPE` 全仓无写入者 ⇒ 海思 CGI 路径、200 字节帧路径、assets 恢复路径**全是死代码**。活的只有 `DeviceUpgradeActivity` 的 72 字节帧与 Ambarella 两条。
4. ⚠️ **更正**：XTU 的 `FLAG_KEEP_SCREEN_ON` 和 WakeLock **只挂在死掉的 Activity 上**，现役传输路径**全程无息屏保护**——审计判为"野外最可能的变砖诱因"。另外我先前写的「MD5 丢前导零」也只对死代码成立，现役 `FileUtils.getFileMD5` 是**正确补零**的。
5. **idGoLive 的固件镜像走 FTP，不是 PTP。** `libcontrol.so` 内嵌完整 `ftplib` + `convert2FtpPath`，PTP 只用于控制面。这解释了它的安全模型：FTP 无传输完整性，唯一闸门是相机收完后的校验。
6. **好消息：镜像本身是自描述的，而且相机会校验。** §5 的真实固件证实：XTU `.bin` 有 256 字节头，内含**型号串**和**版本串**；iCatch `.devfw` 容器内嵌的升级代理会打印 `Start firmware CRC check...`、`Verifying image CRC ... 0x%x != 0x%x failed!`、`Cannot read fw image header!`。⇒ **坏镜像在设备侧会被拒，不必然变砖；而"这镜像是不是给这台的"这个问题 App 本地就能回答——三家都没读那个头。**
7. **版本比较可以统一，但更根本的问题是没人比较。** 三家版本真身都含 `yyyyMMdd`。然而 **TUWIN 的 OTA 路径里完全没有版本比较**（比较权在云端），App 会把**相等甚至更旧**的版本照样装进去。
8. **一旦字节开始流动，三家都无法取消烧录**，都没有相机侧残留清理，都没有恢复模式入口。XTU 甚至在"成功"后删掉本地固件，用户无法重试。
9. **官方写了但没接线的东西**：XTU 九条 `gku_firmware_update_failed_*`（含 battery<10%、无卡、离线、超时、校验失败）**只存在于两个 `R.java`，零功能引用**——厂商知道全部失败模式，一个都没实现。这是本次审计最有力的证据。
10. **App 自更新已移出本文范围**（本项目不通过 App 分发更新）。三家的做法仍作为事实记录保留在 §1.7 / §2.7 / §3.7，但**不再是我们的待办**。

## 3. idGoLive 1.3.6 的固件更新

| 日志 `fw_not_support` | 镜像被拒 / 目标不支持 |
| `JCameraConfig_*`：`enablePTPIP`、`enablePtpReconnection`、`getPtpTimeoutCheckCount/IntervalInSecs`、`setConnectionCheckParam` | 长时刷机期间的 PTP-IP 传输与超时控制 |

**真正的 clean-room 空白（Java 层拿不到，只能抓包）**：PTP 厂商操作码、`SPHOST.BRN` 的容器/头格式、分块尺寸、以及事件 96–100 在线上如何编码。96–100 是 Java 侧的 **SDK 逻辑 ID**；被 strip 过的 `.so` 不暴露任何 vendor-op 符号或操作码串。**只有对真机刷一次固件、同时抓 PTP 流量才能还原。**

## 4. 三家 OTA 横向对比

| 维度 | TUWIN | XTU GO | idGoLive |
|---|---|---|---|
| 云端检版 | `GET newota?version=&boardversion=`（**base URL 字面量未找到**） | `GET /v1/push/api/getNewestVersion`，3 个 **CSV 列表参数**（多设备一次查）；另有 2 代老接口 | 静态 OSS `firmware.json`，**零参数** |
| 匹配键 | `(version, boardversion, model)` | `model-region-hardware` 三元组（缺省 `region="G"`、`hardware="V1.0"`） | `prefix` + `suffix` + 8 位日期 |
| 版本格式 | M3 = `yyyyMMdd`（从 `"Mon DD YYYY"` 归一化）；R3Pro/R6 = 文件名 `HW`/`SW` token，`_`→`.` | `\d{8}` 日期戳，字典序或 int 比 | `_YYYYMMDD_` 三段式，**日期相等也允许重刷** |
| region 门控 | **无** | 有（服务端 + 客户端键） | 有 `area_check` 但**客户端不消费**，实际按 IP 由服务端裁 |
| 下载完整性 | **HEAD 探远端大小** + `IntegrityPolicy.ExpectedSize` + 落点文件名校验 | `.tmp` 后缀 + 失败即删（有个"删整个目录"的 bug） | **完全没有**（无 MD5、不校验长度、无重试） |
| 送包通道数 | 3（REST 整文件 / M3 整文件 / RIDE5 分块） | **4，但只有 1 条可达**（Ambarella + 72B 帧；海思 CGI 与 200B 帧是死代码） | 1（native **FTP over PTP 会话**，非 PTP 对象） |
| 客户端算 MD5？ | R3Pro/R6 有；M3、RIDE5 无 | Amba 有；海思 CGI 无；8080 现役用**正确补零**的 `FileUtils.getFileMD5`（丢前导零的 `BigInteger` 版只在死代码里） | 无（native 算 CRC 随包送出） |
| **装机后回读版本** | **无**——⚠️ 回读只存在于从未被调用的 `DeviceOtaCoordinator`；现役路径上传返回后弹 30 秒倒计时即宣告成功 | **无** | **无**（只有事件 97/98，无版本比对） |
| 感知相机重启 | ⚠️ 只有 RIDE5 一条通道挂了 `FirmwareUpgradeReconnectGate`，且它**不校验任何东西**，只让设备列表继续刷新 | 无（文案让用户自己重启；72B 变体让用户**在相机屏幕上**点升级） | 半有（事件 98 `POWEROFF` → App 自杀） |
| 取消 | 有（`Cancelled` / `bCancelUpload`），但 `FirmwareUploadDialog` 是 `setCancelable(false)` 且 UI **无 CANCEL 态**；R3Pro/M3 走 `lifecycleScope` 无取消标志 | 下载可取消；**送包不可取消**；且二次点击会**再起一条线程共用同一 socket 字段** | 不可取消 |
| 断电/误操作守卫 | 文案 + 事后 `ExternalPowerCheck`；⚠️ **清单里根本没有 `WAKE_LOCK` 权限**，也没有覆盖设备传输的前台服务 | ⚠️ **现役路径零息屏保护**（守卫全在死 Activity 上） | **无任何提示**，无 WakeLock，刷机跑在裸 `new Thread` 上 |
| SD 卡前置 | M3 会分类 `M3SdCardRemoved` / `M3SdCardNotFormatted`，但**只能靠写失败发现**；M3/RIDE5 的 SD 就是暂存介质 | 预检取 `getSdCardInfo`+`getBatteryInfo` 但**返回值被丢弃**；`_failed_battery`/`_failed_nocard` 等**九条**文案存在却零引用 | **强制** `isSDCardExist()`，否则弹 `dialog_no_sd`（唯一被强制的前置条件） |
| 「刷机会恢复出厂」告知 | **有**（`upgrade_firmware_warning`） | 未找到 | 未找到 |
| 本地选文件刷机 | 有代码（`*.appsw` 读取器）但**零调用者** | 有界面 `activity_upload_firmware` 但**宿主 Activity 漏了 manifest 条目** | 有文案（但**路径写错了**，见 3.5） |
| 进度粒度 | 14 态 + 字节 + 百分比 + `routeRevision`（但都是死代码的） | 4 种通道各不同：每块 / 1% / 只写日志 | 下载有百分比；**刷机阶段零进度**，只有转圈 |
| App 自更新（**已移出我们的范围**） | 有（`app_update_*` 12 条文案） | 有（`firmWareModel=XTUGO_Android` + int versionCode + `ACTION_VIEW`） | **未实现**（端点与文案都是死的） |
| 镜像是否自描述 | 未取到样本 | ✅ **256B 头含型号 + 版本 + 长度**（§5.4） | ✅ **`SUNP BURN FILE` 头含长度 + `CHKS` 日期戳**（§5.3） |
| App 是否读镜像头 | ❌ 从不 | ❌ 从不 | ❌ 从不 |

**跨品牌结论**：

1. **「云检版」这一层可以统一，「送包」这一层不能。** 三家检版都是「拿设备自报的三元组去问服务器要 URL」，形状一致；送包却是 3 / 1(活) / 1 条互不兼容的通道。所以我们的 OTA 抽象应该是：**统一的 check/plan 层 + 每 profile 一个 `OtaTransport`**。
2. **版本格式统一成「抽 8 位日期戳」即可覆盖三家。** TUWIN M3、XTU、idGoLive 全都把 `yyyyMMdd` 当版本真身，一个 `FirmwareVersion.from(String): LocalDate?` 工具能通吃。⚠️ 但更根本的问题是 **TUWIN 的 OTA 路径里根本没有版本比较**（比较权在云端），App 会把**相等甚至更旧**的版本照装。
3. ⚠️ **更正：三家都没有「升级后回读版本确认成功」。** TUWIN 那套 14 态状态机与回读逻辑**只存在于从未被调用的 `DeviceOtaCoordinator`**；现役路径上传返回后弹 30 秒倒计时就宣告成功。⇒ 这不再"是官方某家的最佳实践"，而是**官方三家共同的能力空白**，也是我们最该自建的护栏之一（§6.1 R3）。
4. **三家都不做下载完整性**（TUWIN 只探长度、XTU 不解析云端已有的 `size`、idGoLive 完全不校验），也都没有相机侧的失败恢复。而 §5 实测证明：**OSS ETag 就是 MD5、XTU 云端就带 `size`、镜像头部就写着型号与版本** —— 我们不需要任何厂商配合就能把这三件事做对。
5. **设备侧比 App 侧聪明。** 真实镜像里带着 CRC 校验、A/B 双槽（`keep original Firmware1/2`）和 SD 卡更新（`[CardUpdate]`）；三个 Android App 一个都没用上。⇒ 我们做 OTA 的价值主张不是"复刻官方"，而是**把官方漏掉的四道闸门补上**。

## 5. 真实固件镜像实测（本次下载分析）

> 前四节全部来自静态逆向，有个根本盲点：**三个 APK 里没有任何固件样本**（按 `.sw/.appsw/.bin/.brn/.img/.rom/.fw` 全量搜索，只命中 Kotlin 的 `DebugProbesKt.bin`），所以镜像内部结构此前无法回答。本节是**真实镜像的实测结果**。
> 语料与脚本：`_work/firmware/`（`firmware.json`、`C5Pro_{cn,tw,ja}.BRN`、`XTU S7PRO_20.8.6.1.20260910.bin`、`XTUMINI2Pro_V1.8.1.9.20260914.bin`、`analyze.js`、`deep.js`、`tags.js`、`peek.js`）。这些是分析产物，不在仓库里。

### 5.1 获取渠道与合法性

| 品牌 | 是否拿到 | 途径 |
|---|---|---|
| idGoLive（iCatch C5Pro） | ✅ 3 个区域版本 | 公开静态清单 `https://idcam.oss-cn-shenzhen.aliyuncs.com/Firmware/firmware.json`（**GET 无参数无鉴权**）→ 同目录 `SPHOST.BRN` |
| XTU（S7PRO、Mini2Pro） | ✅ 2 个型号 | 公开 API `GET https://server4.gkuvision.com/v1/push/api/getNewestVersion?firm_ware_model=<型号>&region=G&hardware_version=V1.0`（**无鉴权，型号可枚举**）→ `file_url` 指向 `vidvault-asia.oss-cn-hangzhou.aliyuncs.com` |
| TUWIN | ❌ | `newota` 的 base URL 字面量不在反编译产物里（运行时注入），只有下载白名单 `appdownload.tuwinsmart.com` 可猜，未验证 |

顺带两个事实：**XTU 云端可按型号枚举**；`XTUS7` 与 `XTUMAX3` 返回**空列表**——不是所有型号都有 OTA，S7 就没有。

⚠️ 合法性边界：这些是厂商公开给终端用户、接口不做任何鉴权的固件二进制。本节只做结构观察用于互操作，不复制内容、不重新分发。README 已声明厂商固件与商标不在本项目授权范围内。

### 5.2 关键发现：云端其实给了校验信息，三家都没用

| 渠道 | 提供的完整性数据 | App 是否使用 |
|---|---|---|
| 阿里云 OSS 的 `ETag` | 单次上传的 ETag **就是整个文件的 MD5**。实测 `C5Pro_cn.BRN` 的 ETag `15941FC39D4D822F288444891FAE73AB` 与本地 `md5sum` **逐字符相同** | ❌ 从不比对 |
| XTU 云 API | 响应带 **`size`**（如 `54490165`）与 `create_time` | ❌ **App 的 DTO 根本没有这两个字段**（`GetDeviceNewestVersionResponse.java:48-56` 只声明 8 个字段）。实测下载长度与 `size` 完全相等 ⇒ 服务端早就给了，客户端没接 |
| 镜像自身 | 见 5.3–5.5，头部含型号/版本/长度 | ❌ 三家 App **没有一个读过镜像的一个字节** |

⇒ **不需要厂商配合，我们现在就能做「下载后校验 + 校验镜像头部与本机型号匹配」。** 这是本文最重要的一条可执行结论。

### 5.3 iCatch 镜像 = 凌阳 `SUNP BURN FILE` 烧录容器

`C5Pro_*.BRN`：16,110,960 B（cn/tw/th **同尺寸**）、14,780,272 B（ja）。

| 偏移 | 内容 |
|---|---|
| `0x00` | 魔数 **`SUNP BURN FILE\0\0`**（16B）—— Sunplus/凌阳系烧录容器 |
| `0x10` | u32 LE = **文件总长**（`0x00f5d570` = 16110960；cn 与 tw 均实测相等） |
| `0x14` / `0x18` | `0xab600` / `0xac600`（相差 0x1000，疑为 bootcode 段界） |
| `0x1c` | **`0x42c720`** —— 区域化载荷起点 |
| `0x24` | `0xf5d320`（= 文件长 − 624，末条记录偏移） |
| `0x1fc` | **4 字节逐版本不同的摘要**，正落在 ARM 异常向量表尾槽（bootcode checksum 的经典位置）。cn `cc36b5fa` / tw `d9237ea6` / ja `1ba563c4` |

**内部有自描述的版本记录**（`FIFD` 记录 @`0xbdb38`，紧跟 `CHKS` + 构建戳）：

| 版本 | 镜像内 `CHKS` 串 | 镜像内 `{iCatCh}` 串 | 清单 `version` | 吻合 |
|---|---|---|---|---|
| cn | `CHKS25/08/04+27F` | `{iCatCh}50804.10` | `C5Pro_20250804_CK` | ✅ |
| tw | `CHKS25/05/27+23A` | `{iCatCh}50527.09` | `C5Pro_20250527_TW` | ✅ |
| ja | `CHKS25/05/27+254` | `{iCatCh}50527.09` | `C5Pro_20250527_JA` | ✅ |

⇒ **镜像里烙着与云端清单一致的日期戳。** idGoLive 的 `VersionChecker` 只拿相机上报的版本串去比云端字符串，**从不打开文件核对这个 `CHKS`** —— 一条现成的、零成本的错刷防线被浪费。

**前 4.3MB 是 iCatch 的 ROM monitor / cardISP 控制台**，实测串直接暴露了设备侧更新引擎：

```
SUNP BURN FILE   cardISP progress %u/%u   cardISP fail %x   ISP OK
D:\firmware.brn  Example: boot D:\5000TEST.BIN   Read file to DRAM. Ex. read TEST.BIN 0x41000000
:NO_BOOT   :RAWCBOOT0   FW boot error %x
[CardUpdate]update Firmware1.   [CardUpdate]keep original Firmware1.
[CardUpdate]update Firmware2.   [CardUpdate]keep original Firmware2.
spiChipErase  spiBlockErase  nandEraseAll  emmcerase0  erase whole embedded storage
Calculate checksum for specific memory range.
checksum(0x%08x+0x%x) 32:0x%08x, 8:0x%04x
SP5K_RELEASE_VERSION : %s     BASEFW_RELEASE_VERSION: %s
|  iCatch ISP Version [%s.%s]  |     SIDC_MODEL = "iCatch V37"
Copyright (c) 1996-2015 Express Logic Inc. * ThreadX Cortex-A7/GNU Version G5.7.5.2
```

三条**改变风险判断**的结论：
1. **存在 `[CardUpdate]` 卡更新机制** —— 相机可以自己从 SD 卡读镜像刷机。三个 Android App 都没暴露它，但**这就是变砖后的恢复入口**（见 6.1 R9）。
2. **`update Firmware1/2` + `keep original Firmware1/2` 是 A/B 双槽** —— 设备保留原始固件并可回退，大幅降低"必然变砖"的概率。
3. **芯片是 iCatch SP5K 系（Sunplus 血统）+ ThreadX/Cortex-A7** —— 与 §3 的 `HiCam<chip>` 命名、`{iCatCh}` 通道串互相印证。

**区域差异定位**（cn vs tw，尺寸完全相同）：`0x00–0x42c738` 之间**只有 8 + 6 字节不同**（就是上表那两条版本记录），从 `0x42c738` 起 11.2MB 全变 ⇒ **头部 `0x1c` 就是区域化分界**；区域差别不是打补丁，而是多语言资源整段重排。cn vs ja 额外差在头部 `0x11–0x1ff`（长度字段自然不同）。

### 5.4 XTU 镜像有两种**互不兼容**的容器格式

同一品牌、同一云端 API，两种格式，按 SoC 分道。

**(a) S7PRO（SigmaStar/海思系）：256 字节自描述头**

| 偏移 | 内容 | 实测 |
|---|---|---|
| `0x00` | 魔数 8B `15 25 12 08 e3 9c 68 11` | 两型号魔数不同 ⇒ 魔数含版本信息 |
| `0x0c` | u32 LE = **文件总长** `0x045161a8` = 72442280 | ✅ 与实际长度相等 |
| `0x10` | u32 = **256**（头长度） | |
| `0x14` | **32B 型号字段 = `"XTUS7PRO"`** | ✅ |
| `0x54` | **32B 版本字段 = `"20.8.6.1.20260910"`** | ✅ 与云端 `version` 去前缀去 `.G` 后一致 |

外层是 zip（`XTUS7PRO_...G.zip` → 单个 `.bin`），zip 尺寸与云端 `size` 字段**完全相等**。

⇒ **这是最有价值的一条：镜像头里就写着型号和版本，读 64 字节就能回答"这镜像是不是给这台的"。** 而 App 只把文件名和 MD5 发给相机，从不读头。

熵分布另显示 `0x60000–0x430000` 有 3.9MB 平均熵 **1.205**（近乎全零的预留区），另有 768KB 熵 7.894 的压缩载荷 —— 典型分区级镜像 + 预留布局，**刷错就是结构性破坏**。

**(b) Mini2Pro（iCatch 系）：多组件 `.devfw` 容器**

```
0x08 u32 = 144（头长度）   0x0c u32 = 3（条目数）
0x14 + k*0x40 起是 64 字节条目名：
  [0] "bld_pba.devfw"
  [1] "dsp_rom_lnx_rfs_dtb.devfw"
```
容器内嵌**设备侧升级代理**，日志串直接证实校验环节：

```
Start firmware CRC check...
Cannot read fw image header!
Verifying image CRC ... 0x%x != 0x%x failed!
analyzing firmware file: %s
firmware update %s finish
```

⇒ **设备会校验镜像头 CRC 并明确报 validate failed。** 这解释了 idGoLive 事件 99 `FW_UPDATE_CHKSUMERR` 的来源——它是**设备侧** CRC 失败的回报，不是 App 算的。也意味着：**传输截断设备能拒；但"型号对、镜像错"这种逻辑错误只有 App 能防，而三家都没防。**

### 5.5 实测对本文前面章节的修正

| 之前的说法 | 实测后的结论 |
|---|---|
| 「镜像内部结构无法离线研究」 | **推翻**。清单与云 API 均可公开访问，已拿到 5 份真实镜像并解析出头结构 |
| 「`.sw`/`.bin` 是否有可校验的头，无法确定」（XTU 审计的显式空白） | **确定有**：256B 头含型号与版本；iCatch 侧是 144B 头 + 条目表 + 设备端 CRC |
| 「云契约里没有任何 checksum 字段，App 结构上无法校验下载」 | **部分推翻**：XTU 云端**实际返回 `size`**，OSS **ETag 即 MD5**。App 的 DTO 没解析而已 |
| 「iCatch 固件通过 PTP 推送」 | **修正为 FTP**（`libcontrol.so` 内嵌 `ftplib` + `convert2FtpPath`，PTP 只管控制面） |
| 「无 A/B 回退、无卡恢复」 | **修正**：Android App 层确实没有，但**镜像内嵌的 bootcode 有 `[CardUpdate]` 与 Firmware1/2 双槽** |

## 6. 变砖风险审计：三家缺的护栏，以及我们必须自建的

三份安全审计（TUWIN / XTU / idGoLive）合并去重，按「发生概率 × 不可逆程度」排序。**R1–R6 我认为不可妥协**，R7 之后是纵深防御。

### 6.1 护栏清单

| # | 必须自建的护栏 | 缺了会怎样 | 三家现状 | 我们的成本 |
|---|---|---|---|---|
| **R1** | **送包前校验镜像头部 ↔ 本机型号** | 刷入同 SoC 但 sensor/DDR/分区表不同的镜像 → 结构性破坏 | **三家全部：App 从不读镜像一个字节**；XTU 甚至按 4 字符芯片号 `substring(5,9)` 判兼容 | **低**（§5.4 证明头部可读，一次 `pread` + 字符串比对） |
| **R2** | **端到端完整性：下载后与送包前各校验一次** | 截断/位翻转的镜像进入不可逆阶段 | TUWIN 只有 HEAD 探长度；XTU 不解析云端 `size`；idGoLive **完全不校验，且 `onComplete` 在 `close()` 之前触发** | **低**（OSS ETag=MD5、XTU `size` 现成） |
| **R3** | **装机后回读版本 + 硬超时 + 明确的"设备未返回"状态** | 变砖不可检测，用户以为成功 | **三家全无**（见 §0 第 2 条）。TUWIN 有代码但从未接线；idGoLive 靠 97/98 事件但无看门狗，相机不回话就是永久转圈 | 中（需各机型版本读取命令，我们已有 `getDeviceInfo`） |
| **R4** | **息屏/休眠/进程死亡防护：前台服务 + WakeLock + keepScreenOn 覆盖整个传输窗口** | doze 挂起 socket → 相机擦除后等不到数据 → 最经典砖 | **XTU 现役路径零保护**（唯一的 `addFlags(128)` 挂在死 Activity 上）；**TUWIN 清单里根本没有 `WAKE_LOCK` 权限**；idGoLive 有权限但从不申请 | 低-中 |

### 6.2 三家共同的设计缺陷（值得单独记住）

1. **相机只被告知文件名。** XTU 四条通道、TUWIN 三条通道、idGoLive 的 FTP 路径，**没有一条向设备传输型号标识**。设备只能从文件名猜。⇒ 协议层没有"这台机器不该收这个包"的拒绝依据，责任全在 App，而 App 没读镜像。
2. **"记住的协议标志"与"探测出的协议"是两回事。** XTU 用持久化的 Room 列 `isAmba` 选帧格式（R6 的根因），TUWIN 用 `SessionBoundOtaIdentity` 绑会话（做对了）。⇒ 我们的 profile 必须**每次连接重新探测**，绝不把协议选择结果当设备属性缓存。
3. **厂商把失败模式写全了却没实现。** XTU 九条 `gku_firmware_update_failed_*`（battery/nocard/offline/timeout/verify/…）只存在于两个 `R.java`。⇒ 这份文案清单等于厂商替我们写好的需求规格，可直接当我们的状态机。
4. **重复的"孪生死代码"是真实风险源。** XTU 有 `CameraParameters.java` 与拼错的 `CameraParmeras.java` 两份，各带独立的 `IsAmbaDevice`/`MustUpdate` 静态量。⇒ 我们绝不允许协议状态存在第二份真相。

### 6.3 一句话判断

**做 OTA 是可行的，但前提是接受"我们对设备的了解不如它自己的 bootcode"。** 设备侧有 CRC 校验、有 A/B 双槽、有卡更新兜底；App 侧什么都没有。所以正确姿势不是照抄官方 App（那等于照抄一堆死代码和漏检），而是：**把镜像头部校验、完整性、息屏保护、版本回读这四件官方没做的事做出来，再把官方没暴露的卡刷恢复路径暴露出来。** 这四件事成本都是"低"到"中"，而它们正是官方 App 会刷砖的地方。

### 7.3 建议的落地顺序


**第一批（把已有骨架用满，几乎零新协议工作）**

1. **把 `events` Flow 接上** —— 现在两个协议都在发事件、没人收。收进 `AppState` 后，录制状态/电量就不再靠轮询。
2. **A5 关于页 + A2 恢复出厂 + B9 远程重启 + A1 SD 信息与格式化** —— 全塞进现在空着的 Settings Tab，海思命令都已存在。
3. **A3 对时** —— 做成连接流程的一个具名步骤（学 TUWIN），顺带解决相册时间戳问题。
4. **A10 批量选择 + A12 按日分组** —— Files Tab 的两个最大体验缺口。

**第二批（连接与下载，"比官方好用"的主战场）**

5. **A9 连接向导：具名步骤 + 每步失败解法**。
6. **A11 下载管理器 + 前台服务 + 通知**（含 B2 耗时预估与跳过已下载）。
7. **A6 多设备记忆 + A4 改相机 WiFi**。
8. **A14/A15 能力门与收尾保护** —— 把"点了才报错"变成"点之前就告诉你为什么不能点"（与你定的「灰掉的控件必须显示原因」一致）。

**第三批（OTA，单独立项）**

9. **A7 相机固件更新（OTA）** —— 单独立项，且**必须先满足 §6.1 的 R1–R6 才允许对用户开放**。拆法：统一 `check/plan` 层（版本一律归一化成 `yyyyMMdd`）+ 每 profile 一个 `OtaTransport` + 照抄 TUWIN `DeviceOtaOperations` 六方法（`queryUpdate / readVersion / waitForDeviceReady / installUploadedPackage / waitForReboot / reconnect`）与 14 态状态机。
   - **实现顺序按风险从低到高**：先 XTU S7PRO（现役 72B 帧 / Ambarella，且**这是唯一"相机自己在机身 UI 上完成最后一步"的路径，App 侧风险最低**）；再 idGoLive/iCatch（FTP，需自建 CRC 预期）；TUWIN 的 M3/RIDE5 把镜像落到**持久存储**且 `upgrade.cgi` 无参数，风险最高，放最后。
   - **必做的四件官方没做的事**：读镜像头部比对型号（§5.4）、下载后与送包前各校验一次（§5.2）、前台服务 + WakeLock 覆盖整个窗口、装机后回读版本 + 硬超时。
   - **模拟器要同步扩**：加 `fileupload.cgi`/`upgrade.cgi`、一个假的重启与版本变更、以及**"头部型号不匹配就拒绝"的设备侧行为**，否则 OTA 无法在桌面验证，R1 也无处测。
   - **文档要写恢复路径**：把 §5.3 发现的 `[CardUpdate]` 卡刷与 A/B 双槽做成面向用户的救援说明——这是官方有却没讲的事。
