# 固件更新（OTA）与功能差距

> 数据来源：三个官方 APK 的静态逆向，结论标 `path:line`；CONFIRMED = 读到代码，INFERRED = 从命名/上下文推断，未找到 = 搜过且不存在。
> 分析日期 2026-09-20。协议/型号基础事实见 [03-品牌型号与协议矩阵](03-品牌型号与协议矩阵.md)。
> 目的：(1) 把三家「相机固件更新」的实现机制与线上契约挖清楚，作为我们 clean-room 重实现的依据；(2) 盘出我们 App 相比官方的功能缺口并排优先级。

---

## 0. 结论先行

1. **固件更新不是一个功能，是「云检版 + 下载 + 送包 + 相机自己烧」四段**，而三家在「送包」这一段各用了不同传输，XTU 甚至在同一个 APK 里并存 **4 条送包通道 + 3 代云端接口**。所以我们的插件层必须把 OTA 也做成**按 profile 分派**的能力，不能写一个通用上传。
2. **只有 TUWIN 真正闭环了**：它有 14 态状态机、装机后**回读版本比对**、以及靠 SSID 闩锁感知相机重启后重连。XTU 和 idGoLive 都**不检测相机重启完成**，全靠文案让用户自己重启（XTU 的 72 字节变体甚至让用户**在相机屏幕上**点最终升级）。
3. **一旦字节开始流动，三家都无法取消烧录**，也都没有相机侧的残留清理或失败恢复。这是我们继承的硬约束，不是我们没做。
4. **校验和的比对基本发生在相机侧**。TUWIN 的 RIDE3PRO/RIDE6 与 XTU 的 Ambarella/8080 会在客户端算 MD5 并随包声明，但都不回读结果；只有 iCatch 系（idGoLive 与 XTU 的 Mini1）会把 `CHKSUMERR` 作为事件回传。除 TUWIN 外，**下载阶段普遍没有完整性校验**——我们加 MD5+长度校验就是净超越，成本极低。
5. **「App 自更新」和「相机 OTA」在代码里是两套东西**，端点、版本格式、落地文件、最终动作全不同。官方自己也把它们放在相邻包里，很容易搞混——我们的文档与代码要显式分开。（idGoLive 1.3.6 干脆没实现 App 自更新，别把它当缺口。）
6. 版本比较意外地**可以统一**：TUWIN M3、XTU、idGoLive 三家的固件版本真身都是 `yyyyMMdd` 日期戳，一个归一化工具能通吃。
7. 官方有一批**写了但没接线的功能**（XTU 一套 28 态的 OTA 状态机文案，只有 3 条被引用；`_failed_battery`/`_failed_nocard` 已验证只存在于 `R.java`）。这些是免费的现成设计参考，不是我们的缺口。

**(c) 通用 8080，200 字节定长头（`com/gku/rxt/FwUpload2.java`，现役）**

`HOST="192.168.0.1"`、`PORT=8080`、`TIME_OUT=5000`（`:18-20`，已验证）。流程 `run()` `:58-221`：
1. `FwInfo` 流式算 `size` 与 `md5`；
2. `getInfo()` → `new RegisterDeviceToServer(2, size, name, md5).getBuf()` → **200 字节**；
3. connect → 写头 + flush（`:75-77`）；
4. **单次 `read(byte[256])`** 取 ack（`:78-79`）；`<=0` → `"固件>>>读准备状态失败"`，空串 → `"固件>>>解析准备信息失败"`；
5. `ack.trim().startsWith(fwInfo.getName())` 才继续传文件，**1024 字节/块**，每块回调 `progress(sent/available)`（`:122-141`）；否则记 `"没有能够上传固件"` 并关闭；
6. `shutdownInput()+shutdownOutput()` 是**唯一的传输结束信号**，没有 trailer、没有最终 ack 读取。

**200 字节帧逐字段（已验证 `com/hisi/hisiFW/RegisterDeviceToServer.java:25-38`）**

| 偏移 | 长度 | 字段 | 编码 |
|---|---|---|---|
| 0 | 4 | `cmd_type` | int32 **小端** |
| 4 | 4 | `length` = 文件总字节 | int32 小端 |
| 8 | **64** | `data` = 固件**basename**（不是路径） | `String.getBytes()`，无终止符无填充，剩余是 `new byte[200]` 的零 |
| 72 | **128** | `md5` = 十六进制 MD5 | 同上 |
| – | – | 总长恒 **200** | 定长，非长度前缀 |

互操作坑（都要么原样复刻、要么明确决定不复刻）：文件名 >64 字节会**静默覆盖 MD5 槽**，>192 抛 `ArrayIndexOutOfBoundsException`；`String.getBytes()` 未指定字符集；`BigInteger(1,md5).toString(16)` **丢前导零 nibble**（`FwInfo.java:57`、`FirmwareClientThread.java:197`）；`length` 是 int32 → 硬上限 2GiB。

同结构的三份拷贝：`hisilicon/dv/ui/data/model/RegisterDeviceToServer.java:25-38`、`…/FirmRegisterDeviceToServer.java:8-27`、`com/hisi/hisiFW/RegisterDeviceToServer.java:25-38`。另有个 **72 字节** 的无 MD5 兄弟构造器（同文件 `:12-23`），别和下面 `TCP_MSG_S` 的 72 字节帧混。

`FirmwareClientThread`（海思与 SigmaStar 各一份、内容逐字节相同）：connect **超时 10000**、无 soTimeout、IP **硬编码 `192.168.0.1`**；ack 判定同样是「回复以文件名开头」，**不解析 cmd**；分块 10240；进度只 `Log.d` 不上 UI；`sendToCamera(true)` **被调用两次**（`:156-159` 与 `:167-170`，异常路径也发）。全仓找不到 `CopyFileUtils` 的外部调用者 → 判为遗留/死路径。

**(d) 通用 8080，72 字节 `TCP_MSG_S` + ASCII MD5 旁路（现役，设备管理 UI）**

`loginmodule/ui/activity/DeviceUpgradeActivity.java:253-431`（`com/gku/SendSoftActivity.java:95-227` 近乎逐行重复）：

| 「刷机会恢复出厂」告知 | **有**（`upgrade_firmware_warning`） | 未找到 | 未找到 |
| 本地选文件刷机 | 有（`select_firmware_file`，`*.appsw`） | 有（`<appdata>/upgrade/*.sw`、assets `fw/`） | 有文案（但**路径写错了**，见 3.5） |
| 进度粒度 | 14 态 + 字节 + 百分比 + `routeRevision` | 4 种通道各不同：每块 / 1% / 只写日志 | 下载有百分比；**刷机阶段零进度**，只有转圈 |
| App 自更新 | **有**（`app_update_*` 12 条文案，后台续传 + changelog） | **有**（`firmWareModel=XTUGO_Android` + int versionCode + `ACTION_VIEW` 安装） | **未实现**（端点与文案都是死的） |

**四条跨品牌结论**：

1. **「云检版」这一层可以统一，「送包」这一层不能。** 三家检版都是「拿设备自报的三元组去问服务器要 URL」，形状一致；送包却是 3 / 4 / 1 条互不兼容的通道。所以我们的 OTA 抽象应该是：**统一的 check/plan 层 + 每 profile 一个 `OtaTransport`**。
2. **版本比较统一成「抽 8 位日期戳」即可覆盖三家。** TUWIN M3、XTU 三代接口、idGoLive 全都把 `yyyyMMdd` 当版本真身。一个 `FirmwareVersion.from(String): LocalDate?` 工具能通吃。
3. **只有 TUWIN 做到了「升级后回读版本确认成功」和「感知相机重启」**。这两条是官方阵营里最好的工程实践，也是我们应该照抄而另外两家抄不到的。
4. **三家都不做下载完整性（除 TUWIN）**，也都没有相机侧的失败恢复。我们加一个 MD5/SHA + 长度校验就是净超越，成本极低。

### 5.3 建议的落地顺序

**第一批（把已有骨架用满，几乎零新协议工作）**

1. **把 `events` Flow 接上** —— 现在两个协议都在发事件、没人收。收进 `AppState` 后，录制状态/电量就不再靠轮询。
2. **A5 关于页 + A2 恢复出厂 + B9 远程重启 + A1 SD 信息与格式化** —— 全塞进现在空着的 Settings Tab，海思命令都已存在。
3. **A3 对时** —— 做成连接流程的一个具名步骤（学 TUWIN），顺带解决相册时间戳问题。
4. **A10 批量选择 + A12 按日分组** —— Files Tab 的两个最大体验缺口。

**第二批（连接与下载，"比官方好用"的主战场）**

5. **A9 连接向导：具名步骤 + 每步失败解法**。
6. **A11 下载管理器 + 前台服务 + 通知**（含 B2 耗时预估与跳过已下载）。
7. **A6 多设备记忆 + A4 改相机 WiFi**。
8. **A14/A15 能力门与收尾保护** —— 把"点了才报错"变成"点之前就告诉你为什么不能点"（与你定的「灰掉的控件必须显示原因」一致）。

**第三批（OTA，单独立项）**

9. **A7 相机固件更新**。按第 4 节的结论拆成：统一 `check/plan` 层（版本一律归一化成 `yyyyMMdd`）+ 每 profile 一个 `OtaTransport` + 照抄 TUWIN 的 `DeviceOtaOperations` 六方法（`queryUpdate / readVersion / waitForDeviceReady / installUploadedPackage / waitForReboot / reconnect`）与 14 态状态机。
   - **先给海思 CGI 做**（`fileupload.cgi` + `upgrade.cgi`，最简单，且模拟器能演）；再 RIDE3Pro（REST 整文件 + MD5）；Ambarella 与 8080 双分帧放后面。
   - **必须比官方多做的三件**：下载完整性校验（MD5+长度）、**装机后回读版本确认**、刷机会恢复出厂的前置告知。
   - **模拟器要同步扩**：加 `fileupload.cgi`/`upgrade.cgi` 与一个假的重启+版本变更，否则 OTA 无法在桌面验证。
10. **A8 App 自更新** —— 与 OTA 无关，可以并行；GitHub Releases 已经是现成的版本源。

**验证口径**：以上每一项都要在真机（MuMu 起步，最终 XTU 实体机）跑通才算完成；桌面模拟器通过不等于功能可用。
